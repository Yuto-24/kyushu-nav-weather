# エージェントの作業手順とモデル設定

タスクで選択されたモデルが調査・実装・検証を担当し、共通の制約は [AGENTS.md](../AGENTS.md) に従う。

## モデルの切り替えと独立レビュー

| 実装担当 | 独立レビュー担当 |
| --- | --- |
| GPT-6 Astra (`gpt-6-astra`) | GPT-6.1 Sol (`gpt-6.1-sol`) |
| GPT-6.1 Sol (`gpt-6.1-sol`) | GPT-6 Astra (`gpt-6-astra`) |

ユーザーが選択したモデルとreasoning effortを維持する。難易度を理由に別モデルへ切り替えず、
調査・実装・テストの委任はユーザーが求めた範囲に限る。
独立レビューは、実装に参加していない相手モデルを明示した読み取り専用コンテキストで行う。
同じモデルの別エージェントや、実モデル未確認の `/review` は代替にならない。
相手モデルが利用できなければ独立レビューは未完了と報告する。

レビューへ渡すものは、ユーザー要求・受入条件、関連する判断、対象checkoutとbase/HEADまたは差分、
変更ファイル、検証結果と未検証事項。レビュー担当は不足に加え、不要な変更や複雑化も確認し、
根拠・場所・影響とともに必須修正と任意改善を分ける。修正は実装担当が行う。
必須修正後は影響する検証と指摘箇所を確認し、理由なくレビュー全体を繰り返さない。

UI文言は [確認手順](ui_copy_review.md) に従い、Geminiの実行証跡、採用理由、最終実装との照合を残す。
本人指定・仕様了承・既存文言の転用でも確認を省略しない。未確認の文言はPRと完了報告で明示する。

## 設定の置き場所

- プロジェクトの制約と完了条件は `AGENTS.md`、詳細手順は `docs/` に置く。
- `.codex/config.toml` は必要な場合だけ追加する。共通の `model` / `review_model` は固定しない。
- 個人の既定モデル、reasoning effort、権限などのグローバル設定は、このリポジトリの作業に伴って変更しない。
- アプリ管理の環境ファイルは手編集しない。現在の実行モデルや権限を設定ファイルだけから断定しない。

## 調査検証待機の進め方

要求・受入条件、変更ファイル、関連する失敗や指摘から確認し、必要に応じて範囲を広げる。
[知見の索引](knowledge/INDEX.md) と類似実装を確認し、現在の依存関係・コードとの差分を確かめる。
関連資料を一度に全件読み直さず、結果は対象コミットや実行番号と結び付けて保持する。

関連する修正をまとめてから高コストの検証へ進む。検証対象のファイルを実行中に編集しない。
対象が変わった場合は結果の有効性を判断し、影響する検証を再実行する。
生ログの再読、同じ状態の繰り返し取得、根拠のない追加テストを避ける。

### PR提出前のローカル検証

実際の差分と [検証手順](testing.md)、`.github/workflows/verify.yml` を照合し、該当する検証を完了する。
このサービスはPython 3.12とNode 22で動作する。NavMateのDocker test stage、pytest shard、
アプリビルド、FirebaseやLegacyの受入手順は使わない。

Python生成・公開処理が対象なら関係するsuiteを選び、そのsuiteの全件を実行する。
WorkerはNodeのテストと構文検査、静的表示スクリプトは構文と影響する表示を確認する。
文書だけの変更はリンク・記述とコードの整合を確認し、気象取得や画像生成を繰り返さない。
変更に必要なチェックで失敗が残る場合は、原因を解決して再検証する。
未検証の提出をユーザーが明示的に求めた場合を除き、適用する検証が実行不能・失敗のままPRを作成・更新しない。

一度通過した全体検証を、影響しない修正のたびに繰り返さない。
実行コマンド、対象、成功・未実施・実行不能を区別し、独立レビューのモデルと結果もPRへ記録する。

### CI・外部レビューの待機

継続監視を明示的に依頼されていない限り、CI・外部レビューの完了待ち、定期取得、
監視目的のsleep / watch / wait、別エージェントへの監視委任を行わない。
必要なローカル検証と独立レビューを終えてpush・PR作成／更新したら、未完了の検証を明記してターンを終了する。
修正、新コミット、PR本文更新、進捗報告を監視の再開理由にしない。
「結果を確認して」は、その時点の一度の取得を意味する。取得した失敗や指摘への依頼された修正は進められる。
未確認を成功と扱わず、マージや公開の必須ゲートは未解決のまま残す。

## 完了と公開

ローカル検証、hosted CI、公開先の読戻し、自然Cronは、それぞれの証拠で報告する。
通常のPRは `Release: not-required` と理由、`Pending release notes` を記録する。
日次の気象データ更新はアプリの版数リリースとして扱わない。
マージ・本番配置・外部公開の承認はAGENTS.mdと当該ユーザー依頼に従う。
必要な未完了条件を、文章上の「完了」で隠さない。
